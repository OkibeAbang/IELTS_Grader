## Immediate / small (continued)

- [ ] **Listening audio only supports 2-speaker sections.** Fixed (2026-09-27) — Listening audio is no longer the browser's robotic built-in text-to-speech; it's now rendered once per section with Gemini TTS (`gemini-3.8-flash-tts`) using distinct voices per speaker, stored, and served as a real MP3 through a native `<audio>` player (see `server/src/listeningAudio.js`, `server/scripts/renderListeningAudio.js`). Gemini's multi-speaker TTS caps out at exactly 2 speakers per section, which covers every section in the content bank today. If a 3+-speaker script is ever authored (e.g. a Section-3-style group discussion), `generateListeningAudioBuffer` throws clearly rather than silently failing — it'll need a per-turn-synthesize-and-concatenate fallback (synthesize each speaker's lines separately, stitch with ffmpeg, which is already a dependency) before that content can ship. Also: after adding/editing any listening section's script, re-run `npm run render-listening-audio` from `server/` — audio doesn't regenerate itself.
- [ ] **Code review follow-ups on the listening audio rework (2026-09-27).** Nothing here blocked the push, but flagged for before the content bank grows past one section:
  - `AudioScriptPlayer.js`'s `missing` state doesn't reset when `sectionId` changes (no `key` prop at any of the 3 call sites) — a player that 404'd on one section would keep showing "not available" after switching to a different, working section. Unreachable today (only one section exists), will misbehave the moment a second one is added. Fix: add `key={sectionId}` at the call sites, or reset `missing` in a `useEffect` keyed on `sectionId`.
  - `listeningAudio.js`'s `buildSpeakerVoiceConfigs` only handles exactly 2 speakers (throws above that) but has no path for **1** speaker (a monologue) — Gemini's multi-speaker config requires exactly 2 entries, so a future Section 2/4-style single-narrator passage would error out. Needs a branch: 1 speaker → plain `voiceConfig`, 2 → current path, 3+ → existing throw.
  - `audioStorage.js`'s Range-header parser (`/bytes=(\d*)-(\d*)/`) mishandles suffix ranges (`bytes=-500` should mean "last 500 bytes," parses as `start=0` instead). Low risk — browsers' `<audio>` elements typically send forward ranges — but a real spec deviation on a public route.
  - `audioStorage.js`'s `streamListeningAudio` route does a `HeadObjectCommand` existence check *and* a separate `GetObjectCommand` — two R2 round-trips per audio load in production instead of one. Simpler: attempt the `GetObjectCommand` directly and catch NotFound for the 404 case.
  - Nitpicks: the Gemini API key rides in the TTS request's URL query string (`?key=...`) — matches Google's own documented convention and this only runs from a manual script, but `x-goog-api-key` as a header is the alternative if it ever matters; no timeout on that `fetch()` call (fine for a script you're watching run); the player's "not available yet" error message assumes a missing file rather than e.g. a transient network blip mid-stream.
